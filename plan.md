# Executive Summary

ApartmentBuyingAgents DK is an open-source, AI-native property purchasing platform designed specifically for the Danish housing market.

The platform combines:

* Multi-agent reasoning
* Danish housing market intelligence
* Danish banking rules
* Property due diligence
* Macroeconomic analysis
* Negotiation support
* Financial simulations

The goal is to create the equivalent of TradingAgents for Danish real estate.

A buyer should be able to provide:

* A Boligsiden URL
* An estate agent URL
* Property documents
* An address
* Personal financial information

And receive a comprehensive buyer assessment generated by a team of specialized AI agents.

The platform starts as a terminal-first application and evolves into a Denmark-wide property intelligence platform.

---

# Vision

Buying a property is one of the largest financial decisions most Danes will ever make.

Today buyers must gather information from:

* Estate agents
* Banks
* Lawyers
* BBR
* Tinglysning
* Boligsiden
* Municipal planning portals
* Ejerforening documents

The information is fragmented.

ApartmentBuyingAgents DK aims to centralize these sources and provide transparent, explainable recommendations.

The platform should answer:

* Can I afford this?
* Would a Danish bank approve me?
* Is this fairly priced?
* What are the risks?
* What should I bid?
* Should I buy now or wait?
* Is this apartment better than the alternatives?

# Core Principles

## Human Decision Support

The system assists buyers.

It does not replace:

* Banks
* Lawyers
* Building experts
* Surveyors

## Source Transparency

Every conclusion should be traceable to:

* Data
* Documents
* Calculations
* Agent reasoning

## Deterministic Finance

Financial calculations must never rely on LLMs.

LLMs explain results.

Calculation engines produce results.

## Open Source

The platform should be fully open source.

Community contributions should be encouraged.

## Denmark First

The system is built specifically for Denmark.

International expansion is not a priority.

# Agent System

## Buyer Committee Agent

The orchestrator.

Responsibilities:

* Coordinate all agents
* Aggregate findings
* Resolve disagreements
* Generate final recommendations

Produces:

* BUY
* MAYBE
* AVOID

---

## Listing Agent

Responsibilities:

* Parse listings
* Extract facts
* Normalize data

Extracts:

* Price
* Address
* Area
* Rooms
* Balcony
* Elevator
* Floor
* Energy label
* Monthly owner costs
* Build year

---

## Market Comps Agent

Responsibilities:

Determine whether a listing is fairly priced.

Analyzes:

* Comparable sales
* Comparable listings
* Area price trends
* Price per square meter
* Days on market
* Historical price changes

Produces:

* Fair value estimate
* Price confidence interval
* Overpriced/underpriced score

---

## Market Temperature Agent

Purpose:

Analyze macroeconomic and housing market conditions.

This is the macroeconomic intelligence layer.

### National Analysis

Tracks:

* Interest rates
* Inflation
* Employment
* Wage growth
* Mortgage activity
* Housing supply
* Consumer confidence

### City Analysis

Tracks:

* Price growth
* Sales activity
* Inventory
* New construction
* Population growth

### Neighborhood Analysis

Tracks:

* Local price trends
* Inventory
* Sales velocity
* Demand pressure

Produces:

* Market Heat Score
* Buyer Power Score
* Seller Power Score
* Liquidity Score
* Negotiation Score
* Price Risk Score

Output Example:

```json
{
  "market_temperature": "warm",
  "buyer_power": "medium",
  "liquidity": "high",
  "price_risk_12_months": "low"
}
```

## Danish Credit Agent

Most important module.

Purpose:

Simulate a Danish bank's approval process.

Analyzes:

* Income
* Savings
* Debt
* Household composition
* Housing costs
* Mortgage structure

Calculates:

* Debt factor
* Loan-to-value
* Disposable income
* Stress test results
* Affordability score

Produces:

* Approval likelihood
* Maximum purchase price
* Maximum safe purchase price

---

# Danish Bank Credit Engine

Separate deterministic package.

Structure:

```text
dk_bank_credit_engine/

  debt_factor.py
  affordability.py
  mortgage.py
  stress_test.py
  approval_score.py
```

Rules should model:

* Rådighedsbeløb
* Gældsfaktor
* Belåningsgrad
* Realkredit financing
* Bank loans
* Interest-rate stress testing

LLMs never perform calculations.

# Delivery Roadmap

These are product delivery phases.

The UI phases in the Technology Strategy section are interface milestones and can overlap with the delivery phases below.

Execution details live in `todo.md`.

## Phase 0 - Foundation & Contracts

Goal:

Turn the document into a runnable project skeleton with stable interfaces.

Primary outputs:

* Repository scaffolding
* Core domain models
* Agent and tool contracts
* Test harness
* Sample fixtures

To-dos:

* Create the initial repository structure under `src/`, `tests/`, `examples/`, and `docs/`
* Define core models for `Listing`, `BuyerProfile`, `DocumentBundle`, `MarketSnapshot`, and `AnalysisReport`
* Define standard agent input/output schemas, including citations and confidence levels
* Separate deterministic finance code from LLM-driven explanation code
* Add configuration and secrets handling for local development
* Add a small fixture library with sample listings, buyer profiles, and property documents
* Add baseline unit tests and one end-to-end smoke test with mocked data

Exit criteria:

* A developer can run one mocked apartment analysis locally from the TUI

---

## Phase 1 - MVP Single Apartment Analysis

Goal:

Deliver a useful first version for analyzing a single apartment in Aarhus.

Primary outputs:

* TUI shell
* URL analysis flow
* Credit engine v1
* Basic report generation

To-dos:

* Build the Textual TUI shell and main menu
* Implement listing parsing for Boligsiden and estate agent URLs
* Implement the Danish bank credit engine v1 for affordability and stress testing
* Implement the Buyer Committee orchestrator
* Implement the first agent set: Listing Agent, Market Comps Agent, Danish Credit Agent, Negotiation Agent, and Red Team Agent
* Generate a Markdown buyer report with assumptions, findings, and recommendation
* Add structured logging and error handling for missing or partial source data
* Validate the workflow on a small set of Aarhus apartments

Exit criteria:

* A user can provide a listing URL and buyer profile and receive a report with a clear recommendation

---

## Phase 2 - Due Diligence Depth

Goal:

Move from listing analysis to document-backed buyer due diligence.

Primary outputs:

* Document ingestion
* Risk scoring
* Specialized due diligence agents
* Expanded report formats

To-dos:

* Build document ingestion for PDFs, images, and copied text
* Implement the Ejerforening Agent using budgets, minutes, and maintenance plans
* Implement the Legal Agent using ownership, easement, and restriction checks
* Implement the Building Agent using condition-related source material and extracted findings
* Normalize scores so agent outputs can be compared and aggregated consistently
* Add evidence sections and unresolved questions to the final report
* Generate bank meeting briefs and lawyer review briefs
* Add regression tests for document parsing and risk aggregation

Exit criteria:

* A user can provide a listing plus key documents and receive a traceable due diligence report

---

## Phase 3 - Discovery, Comparison & Watchlists

Goal:

Help users choose between apartments instead of only analyzing one listing at a time.

Primary outputs:

* Search workflows
* Saved apartments
* Comparison views
* Watchlists

To-dos:

* Build apartment search with filters for city, price, area, rooms, and features
* Add local storage for saved apartments, notes, and rerun history
* Implement comparison workflows across price, affordability, risks, and negotiation potential
* Add watchlist tracking and change detection for price or listing updates
* Extend the Negotiation Agent with comparable-based bid framing
* Add explainable ranking logic so users understand why one listing scores above another
* Validate the search and comparison flow in Aarhus and Copenhagen

Exit criteria:

* A user can search, shortlist, compare, and revisit multiple apartments in one workflow

---

## Phase 4 - Multi-City Intelligence

Goal:

Expand geographic coverage and strengthen market context.

Primary outputs:

* City adapter framework
* Multi-city support
* Location intelligence
* Scenario inputs for market analysis

To-dos:

* Formalize the city adapter interface and shared data requirements
* Harden the generic adapter for fallback coverage
* Implement the Copenhagen adapter
* Add adapters for Aalborg, Odense, Frederiksberg, and major municipalities
* Implement the Location Agent integrations for flood, noise, transport, and planning data
* Expand the Market Temperature Agent with city and neighborhood pipelines
* Feed the What-If Agent with stable scenario inputs from finance and market data
* Benchmark quality, runtime, and operating cost across city adapters

Exit criteria:

* The same core workflow works across multiple major Danish housing markets

---

## Phase 5 - Productization & Community Ecosystem

Goal:

Turn the local tool into a broader product and contributor platform.

Primary outputs:

* Web application
* Hosted workflows
* Plugin model
* Community contribution path

To-dos:

* Add a web application on top of the core analysis services
* Add persistent sessions and hosted report access if SaaS deployment is pursued
* Package report generation for HTML and PDF delivery
* Define a plugin or extension model for community agents and skills
* Add observability, rate limiting, background jobs, and operational safeguards
* Publish contribution guides, validation benchmarks, and example datasets
* Define governance for source quality, evaluation standards, and review criteria

Exit criteria:

* The project is usable beyond the terminal and ready for external contributors

---

## Cross-Cutting Workstreams

These should run through every phase:

* Data quality and source provenance
* Deterministic finance validation
* Strong test coverage and regression fixtures
* Prompt and agent evaluation
* Runtime cost and latency tracking
* Privacy and sensitive financial data handling
* Report explainability and citation quality

Test coverage should be treated as a product requirement, not cleanup work after implementation.

At minimum, every major workflow should have:

* focused unit tests
* integration or smoke tests across service boundaries
* regression fixtures for parsers, finance calculations, and reports
